## Root-cause finding for the 2 `unresolved-attribute` errors

`apps/api/src/api/utils/coralogix_grpc_utils.py:152,163` reference **non-existent** enum members. The canonical `alert_def_type.proto` at `libs/common/proto/com/coralogixapis/alerts/v3/alert_def_type.proto` defines:

- `ALERT_DEF_TYPE_LOGS_IMMEDIATE_OR_UNSPECIFIED` (value 0) — **not** `ALERT_DEF_TYPE_LOGS_IMMEDIATE`.
- `ALERT_DEF_TYPE_SLO_THRESHOLD` (value 18) — **not** `ALERT_DEF_TYPE_SLO`.

The rest of the codebase already uses the correct names (`libs/common/src/common/clients/coralogix_grpc_client.py:1881`, `libs/common/src/common/schemas/grpc_schemas.py:360,384`, `apps/api/openapi.json` enum list). So this is a real bug — the map here would raise `AttributeError` at import time if the module were reached. It is imported by `apps/api/src/api/services/alerts_service.py` (verify — indirectly through utility usage), so if it's reachable it would already have broken; likely the two branches for `LOGS_IMMEDIATE` / `SLO` were never hit at runtime. **Fix at the root** by using the correct enum names and delete the `# type: ignore[unresolved-attribute]` comments. No `ty: ignore` needed here.

### 6. `src/api/agent/**` — remove the `--exclude src/api/agent` carve-out

Removing the exclude will surface whatever ty 0.0.59 reports on agent code. From PR #460's diff we know today's shape of suppressions there; the ticket's stricter constraint means:

- **First try**: fix at the source. Real fixes are preferred over suppression.
- **Second**: if a suppression is genuinely required, use scoped `# ty: ignore[<specific-code>]` (never blanket `# ty: ignore`, never `# type: ignore` — those are mypy syntax and don't apply to ty).
- **Never**: keep a `# type: ignore[…]` intended for mypy on a line whose sole checker is now ty. Convert each such comment into either a real fix or a `# ty: ignore[…]`.

Concretely, iterate this loop until `uv run ty check` (no `--exclude`) exits 0:

1. Run `uv run ty check` from `apps/api/`.
2. For each error/warning, in this order of preference:
   - Fix the underlying typing issue (e.g., narrow the union with `isinstance` / `match`, cast to the right TypedDict, use `agents.helpers.narrow_...` if available in OpenAI-Agents SDK, or introduce an explicit local variable annotation).

3. Also address `warning[unused-type-ignore-comment]` — remove every one that ty flags as unused.

## Edge cases / risks

- **Proto-generation carve-out**: locally, `common/generated/**` isn't populated unless `just common::proto` was run (requires SSH access to Coralogix proto repos). If ty in CI fails on unresolved-import for a proto module, add it to `[tool.ty.analysis].allowed-unresolved-imports` in `apps/api/pyproject.toml` — but only after verifying it's actually a CI issue, not local-only.
- **`AlertDefType.ALERT_DEF_TYPE_LOGS_IMMEDIATE_OR_UNSPECIFIED` semantics**: value 0 is the proto-3 default, so any deserialized `AlertDefType` that was unset would map here. The user-visible mapping is that a request for `"LOGS_IMMEDIATE"` gets a filter value of "logs immediate OR unspecified". This matches sibling code at `libs/common/src/common/schemas/grpc_schemas.py:360`, so behavior is consistent with the rest of the codebase.
- **`skip_mypy` argument in callers**: after removing `*_flags` from the justfile signatures, any caller still passing `skip_mypy` will error. Grep the repo for `just lint skip_mypy` — only `.github/workflows/ci.yaml:295` uses it. Update both together in one PR.
- **`[tool.mypy]` config removal**: this file has module-specific `ignore_errors` for `common.generated.*`. ty already handles generated protos via `allowed-unresolved-imports`; no equivalent needed for `ignore_errors`. If ty starts reporting on `common.generated.*`, add an `exclude` to `[tool.ty.src]`.
- **PR #460's `*_flags` shim**: PR #460 kept `lint *_flags:` as a compat shim because it couldn't update `ci.yaml`. We can update `ci.yaml` in the same PR, so we drop the shim entirely — cleaner.
- **Latest ty vs. 0.0.55**: PR #460 pinned to 0.0.55. "latest" (0.0.59) may introduce new diagnostics; if any are genuinely wrong (ty false positives), file a bug and use a narrow `# ty: ignore[<code>]` with an inline link to the upstream issue. If the diff between 0.0.55 and 0.0.59 introduces broad noise, fall back to 0.0.55 explicitly and document why in the PR description.
- **`backend-guide.md` mentions mypy**: `.claude/rules/backend-guide.md` says "Type Checking: mypy". Non-blocking, but ideally patch to "ty" in the same PR — it's a docs-only line and matches the ticket spirit. Check with reviewer before including.
